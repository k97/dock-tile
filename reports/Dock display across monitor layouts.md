# Exposed edges decide where the Dock lands

With "Displays have separate Spaces" on, macOS moves a bottom Dock to whichever display the pointer *pushes against* along a stretch of bottom edge that is an outer edge of the whole desktop. A stretch that another display touches is a seam, and the Dock never goes there. With the setting off, the Dock stays on the main display (the one with the menu bar) and ignores the pointer. Every arrangement question reduces to one computation: take the anchor's Dock edge and subtract every interval another display touches. If anything is left, a warp-and-push can work. If nothing is left (identical displays stacked, a narrower display sitting inside a wider one's span, the top row of a 2×2 grid), no pointer motion, real or synthetic, can bring the Dock there. The tool should say so and stop trying. Apple documents none of this. The rules come from community reports, a single Apple DTS anecdote, and the code of seven Dock-pinning tools. macOS 15.0 briefly broke even partly exposed seams, and 15.1 restored them. Among the prior art, only the open-source DockPin models exposed edge intervals: it presses on the midpoint of the longest free stretch and refuses to lock onto a display whose edge is fully covered. Dock Tile's uncommitted change already adopts the interval model. The rest of this report covers what the tool should do around that model: detection, retries across stretches, restoring the cursor, wake handling, and a clear message when there is no free edge.

## macOS moves a bottom Dock only through an exposed edge stretch

**The trigger is sustained pressure against an edge, not a touch.** The only Apple-staff description comes from a DTS engineer, who hovers "at the bottom of the monitor's screen for a few seconds and the dock moves over" with auto-hide on ([Apple Developer Forums 764007](https://developer.apple.com/forums/thread/764007)). Consumer guides say you must "keep sliding down for it to work reliably" ([OWC](https://eshop.macsales.com/blog/48027-how-to-move-the-dock-from-one-monitor-to-another-on-a-mac/)). No source gives a band height, an event count or a dwell time. The tools' constants are hand-tuned. Reliability also depends on *where* along the edge you push. Users report roughly 30% success mid-edge and near-certain success at the far ends of a stretch that does not line up with the neighbouring screen ([OWC / Apple Community summary](https://eshop.macsales.com/blog/48027-how-to-move-the-dock-from-one-monitor-to-another-on-a-mac/)). Dock Tile's own code records the same thing: teleporting straight onto the edge worked about one time in three, and gliding in fixed it (local: `DockTile/Managers/DockLockManager.swift`).

**Only exposed edge stretches qualify.** "The Dock cannot be placed at the bottom of a display if another display is immediately below it" ([Apple Community 255763872](https://discussions.apple.com/thread/255763872)). The DockLock developer says the Dock cannot reach a display whose bottom edge is "perfectly aligned or overlapped with another screen", and that a few pixels of offset in Arrange Displays fixes it ([Apple Community 256165313](https://discussions.apple.com/thread/256165313)). On Tahoe 26.1, identical stacked monitors keep the Dock "always" on the lower one, even when the upper one is the main display ([Apple Community 256192595](https://discussions.apple.com/thread/256192595)). DockPin's maintainer says the same: "macOS will only show the Dock on screen edges that are 'external' … there's no API or workaround for this". The reporter in that thread unblocked a 2×2 layout by dragging the lower monitor "down just a bit" ([DockPin #1](https://github.com/green2grey/DockPin/issues/1)). The prediction rule follows directly: **candidate edge = the display's Dock edge minus every interval where another display's opposite edge touches it**. Mismatched widths therefore help, because a wider upper display has free stretches either side of a narrower one below.

**The main display is the fallback home, and separate Spaces is the master switch.** With "Displays have separate Spaces" off, "the dock and menu bar only appear on the display I have set as the main display" ([MacRumors 2446351](https://forums.macrumors.com/threads/hide-menubar-but-keep-window-snapping.2446351)). Turning the setting off is the standard advice for stopping the Dock from jumping, and the change needs a log-out ([Apple Community 251134915](https://discussions.apple.com/thread/251134915)). Making another display the main display moves the Dock and the menu bar there together ([Setapp](https://setapp.com/how-to/how-to-move-dock-on-mac-to-a-second-monitor)). The OS also moves the Dock on its own. DockAnchor's code says "macOS resets the Dock to the primary display on wake" ([DockAnchor DockMonitor.swift L248–L324](https://github.com/bwya77/DockAnchor/blob/HEAD/DockAnchor/DockMonitor.swift#L248-L324)). The DockLock developer says the app "cannot prevent that" and relocates afterwards ([DockLockPro #9](https://github.com/JulyIghor/DockLockPro/issues/9)). A commenter reports that attaching a screen below the main one moves the Dock onto the new screen ([DockAnchor #16](https://github.com/bwya77/DockAnchor/issues/16)).

**Side Docks follow the same rule, which explains the "outermost display" folklore.** Macworld (2016) says a left Dock stays on the leftmost display, or on the topmost when displays are stacked ([Macworld](https://www.macworld.com/article/228695/how-to-move-the-dock-about-and-where-it-will-never-ever-reside.html)). Apply the exposed-edge rule to the left edge and that is what you get. Side by side, only the leftmost display has a free left edge. Stacked vertically, every display has one. My inference is that the stacked case is the only side-Dock layout where a move is possible, and it is also where the reports conflict. In 2016 the Dock went to the topmost display. A 15.7.2 report says a right-edge Dock on stacked displays used to follow the hovered screen and now sits only on the bottom (main) one ([Apple Community 256184856](https://discussions.apple.com/thread/256184856)). Some guides claim pointer movement doesn't work for side Docks at all ([Setapp](https://setapp.com/how-to/how-to-move-dock-on-mac-to-a-second-monitor)). DockAnchor, DockPin and Still Dock nonetheless support left and right Docks ([stilldock.com](https://stilldock.com)). Treat stacked side-Dock placement as unpredictable until measured.

**Auto-hide does not change the rule but blinds detection.** Macworld says a bottom Dock follows the pointer "whether or not auto-hide is on" ([Macworld](https://www.macworld.com/article/228695/how-to-move-the-dock-about-and-where-it-will-never-ever-reside.html)), and the DTS engineer's working method used auto-hide ([Apple Developer Forums 764007](https://developer.apple.com/forums/thread/764007)). Auto-hide is still where the tools break: DockGuard "may not work", and Still Dock's App Store build "stops working" ([DockGuard init.lua](https://github.com/ohyoungpark/DockGuard.spoon/blob/HEAD/init.lua#L22); [stilldock.com](https://stilldock.com)). The likely reason is that an auto-hidden Dock reserves no `visibleFrame` on any screen, so the cheapest detector goes blind.

**Version history: one real regression, then quiet.** On macOS 15.0 the Dock could no longer reach a display that had another display below it, even across a partly exposed seam. The thread drew ~202 "me too" votes ([Apple Community 255762225](https://discussions.apple.com/thread/255762225)). Apple fixed it in 15.1 beta 6 (24B5046f) and shipped the fix in 15.1 (24B83) ([Apple Developer Forums 757581](https://developer.apple.com/forums/thread/757581); [Apple Community 255762225](https://discussions.apple.com/thread/255762225)). The fully-covered case was never "fixed" and is probably by design, because the upper display has no outer bottom edge. Late-2025 reports on 15.7.x and Tahoe 26.1 show no new Dock-display setting ([Apple Community 256192595](https://discussions.apple.com/thread/256192595)). Tahoe 26.4 has a DisplayLink bug that reserves Dock space on more than one display ([DisplayLink forum t-69877](https://www.displaylink.org/forum/archive/index.php/t-69877.html)). For macOS 27 I found no change to the Dock-display rules. The one 27-specific report is that ⌘Tab now appears on the active window's screen rather than the Dock's, which DockLock calls a system limitation ([DockLockPro #11](https://github.com/JulyIghor/DockLockPro/issues/11)). DockLock needed an update for 27 ([App Store](https://apps.apple.com/app/docklock-lite/id6741814079)), and DockAnchor has an open "not working after restart" report on the 27 beta ([DockAnchor #29](https://github.com/bwya77/DockAnchor/issues/29)).

**Virtual and mirrored displays are thinly documented.** An AirPlay display took part in the normal edge rule ([Apple Community 256165313](https://discussions.apple.com/thread/256165313)). An iPad (Sidecar) placed *below* the main monitor blocked the Dock from returning to the main monitor "offset or not". That contradicts the rule and is unresolved ([Apple Community 256165313](https://discussions.apple.com/thread/256165313)). DockLock's developer, on a wider display over an iPad, says the Dock may "still jump down" on reconnect and the app moves it back ([DockLockPro #4](https://github.com/JulyIghor/DockLockPro/issues/4)). I found nothing on where the Dock goes with mirrored displays, with a sleeping or powered-off display, or in clamshell mode. Quartz semantics are the only guide there. The active display list is "connected, awake, and available for drawing", and with hardware mirroring a display "may be online but not necessarily active or drawable" (SDK headers, CGDirectDisplay.h / CGDisplayConfiguration.h; see [Apple archive, Notification of Configuration Changes](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/QuartzDisplayServicesConceptual/Articles/Notification.html)).

## Synthetic pushes count only as events, never as a cursor position

**A warp alone can never move the Dock.** `CGWarpMouseCursorPosition` and `CGDisplayMoveCursorToPoint` move the cursor, and "calling either of these functions does not generate a mouse event" ([Apple archive, Controlling the Mouse Cursor](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/QuartzDisplayServicesConceptual/Articles/MouseCursor.html)). DockLock (omaralzare) blocks the Dock by dropping downward `deltaY > 0` packets at a session tap, while the cursor still reaches the edge ([omaralzare/DockLock](https://github.com/omaralzare/DockLock)). So the Dock evidently reads the event stream, deltas included, and not the cursor position. A move therefore needs posted `mouseMoved` events with a non-zero delta pointing past the edge. Every working tool posts them from an HID-state source at `.cghidEventTap`, which sits upstream of the session tap ([DockAnchor L675–L798](https://github.com/bwya77/DockAnchor/blob/HEAD/DockAnchor/DockMonitor.swift#L675-L798)). Whether posting at the session tap would also work is untested anywhere. A tool that posts while its own clamp tap is active must either suspend that tap or whitelist its own events. DockAnchor tags its events with `eventSourceUserData`.

**Suppression and permissions fail silently.** After a posted event, local hardware motion is suppressed for **0.25 s by default** per event source. A game developer measured the cursor sticking for exactly that long and fixed it with `CGEventSourceSetLocalEventsSuppressionInterval(source, 0)` ([Colin Cornaby](https://www.colincornaby.me/2023/02/mac-games-and-cursor-warping-weirdness/)). Wine and SDL do the same ([wine-cvs](https://www.winehq.org/pipermail/wine-cvs/2015-October/109535.html)). Inside a push the suppression helps, because the user's hand can't fight the push. After the push it hurts, because the user's mouse freezes for a quarter of a second. Posting events needs its own grant: `CGPreflightPostEventAccess` exists separately from `AXIsProcessTrusted`. On Sequoia a helper saw the post check return false while the Accessibility check returned true, and DTS said to grant the process that actually creates the tap ([Apple Forums 758554](https://developer.apple.com/forums/thread/758554)). `CGEvent.post` returns nothing, so a missing post grant looks exactly like "the Dock refused". Revoking Accessibility while an active tap runs can freeze system input ([DockAnchor #10](https://github.com/bwya77/DockAnchor/issues/10); [Apple Forums 844416](https://developer.apple.com/forums/thread/844416)).

**Geometry lives in Quartz global points.** `CGDisplayBounds` returns a display's bounds in global coordinates: origin at the main display's top-left corner, y pointing down, in points. Mixed Retina scales therefore need no pixel conversion when warping. `NSScreen.frame` and `visibleFrame` use a bottom-left origin and must be flipped against the main display's height ([Apple archive, Display Info](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/QuartzDisplayServicesConceptual/Articles/DisplayInfo.html)). One cheap check guards every push: `CGGetDisplaysWithPoint` on the point 1 pt past the edge. A non-empty result means a neighbour is there, and the cursor will cross onto it instead of pressing.

**Detecting the Dock's display has no public API.** DockAnchor reads the Dock process's first AX window position ([DockAnchor L801–L834](https://github.com/bwya77/DockAnchor/blob/HEAD/DockAnchor/DockMonitor.swift#L801-L834)). mac-dock-lock picks the screen with the largest `frame`−`visibleFrame` inset over 2 pt, and returns "unknown" when auto-hide is on ([mac-dock-lock main.swift L431–L454](https://github.com/darrenoakey/mac-dock-lock/blob/HEAD/Sources/main.swift#L431-L454)). DockCleat gives up: "There's no reliable API to detect which screen the Dock is on" ([dock-cleat](https://github.com/aitiotekt/dock-cleat/blob/HEAD/DockCleat/DockMonitorService.swift)). The private `CoreDockGetOrientationAndPinning` returns the orientation only ([Ghostty Dock.swift mirror](https://git.uoc.run.place/Applied-Software/ghostty/src/branch/vm-tests/macos/Sources/Helpers/Dock.swift)). Dock Tile tries `visibleFrame` first, then the largest Dock-owned CGWindow. No other tool uses that second method, and nobody has measured its reliability on 15, 26 and 27.

## Seven tools share one technique; only DockPin models shared edges

Every open-source tool blocks the Dock the same way: an active CGEvent tap (`.cgSessionEventTap`, `.defaultTap`, Accessibility required) over a thin band on the non-anchor displays' Dock edge. They differ in three places: what they do with the event, how wide the band is, and how they move the Dock back.

| Tool | Block | Band | Move on demand | Detect Dock display | Shared edges |
|---|---|---|---|---|---|
| DockAnchor (~600★, active) | drop `mouseMoved` (`return nil`) | full edge width, 10 px | hide cursor, warp 50 px in, 8 posted moves @15 ms + 8 @25 ms (HID), warp back | AX window position | none: blocks whole edge |
| DockPin (~24★, active) | rewrite location 7 px inward; mask includes drags; Option overrides | exposed intervals only, −5…+2 px | 3 warp+post steps 70 ms apart, 200 ms wait, warp **and post** back; midpoint of longest exposed interval | none | subtracts neighbours (2 pt tolerance, >0.5 pt kept); refuses unreachable anchors and warns |
| DockCleat, mac-dock-lock | DockAnchor clones | full edge, 10 px | mac-dock-lock: 8 steps @30 ms + 10 @80 ms, ≤5 attempts | mac-dock-lock: `visibleFrame` inset | none |
| DockGuard.spoon | post a move 1 px up | any screen's bottom 1 px | none | none | none |
| DockLock Lite/Plus (commercial) | unpublished; "no extra permissions" | bottom only | relocates after wake to first allowed screen | unpublished "engine modes" | requires a few exposed pixels |
| Still Dock (commercial) | "keeping your pointer away from the divider" | bottom/left/right | "Move Dock to This Screen" (Accessibility) | unpublished | unpublished |

Sources: [DockAnchor](https://github.com/bwya77/DockAnchor/blob/HEAD/DockAnchor/DockMonitor.swift#L916-L943), [DockPin DockMonitor.swift](https://github.com/green2grey/DockPin/blob/HEAD/Sources/DockMonitor.swift#L227-L248), [DockPin DockReanchorer.swift](https://github.com/green2grey/DockPin/blob/HEAD/Sources/DockReanchorer.swift#L13-L71), [DockPin DisplayLayoutAnalyzer.swift](https://github.com/green2grey/DockPin/blob/HEAD/Sources/DisplayLayoutAnalyzer.swift#L59-L181), [mac-dock-lock](https://github.com/darrenoakey/mac-dock-lock/blob/HEAD/Sources/main.swift#L252-L327), [DockGuard](https://github.com/ohyoungpark/DockGuard.spoon/blob/HEAD/init.lua#L44-L69), [DockLock FAQ](https://docklockpro.com/faq/), [stilldock.com](https://stilldock.com).

**DockPin is the closest prior art, and its unreachable-anchor policy matters most.** When a chosen display's edge has no exposed interval, DockPin drops that display from the allowed set. If no allowed display remains, it builds **no** blocked zones at all, so the pointer is never trapped. It shows a warning that "the current display arrangement blocks the selected edge" ([DockPin README](https://github.com/green2grey/DockPin); [DockMonitor.swift L101–L129](https://github.com/green2grey/DockPin/blob/HEAD/Sources/DockMonitor.swift#L101-L129)). Its constants (2 pt adjacency, 0.5 pt minimum stretch) are unexplained. DockLock's "a few pixels must be exposed" is just as unmeasured ([App Store](https://apps.apple.com/app/docklock-lite/id6741814079)). Nobody knows the narrowest stretch macOS accepts.

**The commercial tools probably do not drop events.** Still Dock's App Store build needs no permission. It "stops working while the Dock is set to auto-hide", and "a determined drag can still get through" ([stilldock.com](https://stilldock.com)). That fits an unprivileged global mouse monitor plus a warp, which cannot swallow events. This is my inference; neither vendor confirms it. The DockLock developer's own statements contradict each other: it "hooks into the system's Dock-relocation logic", uses "native macOS Accessibility APIs", and works with "no private APIs" ([DockLock FAQ](https://docklockpro.com/faq/); [MacRumors](https://forums.macrumors.com/threads/docklock-pro-finally-fix-macos-dock-jumping-on-multiple-monitors.2450246/)).

## Wake, drags and bare-warp restores cause most field failures

The issue trackers fall into a handful of classes, and each traces to a specific design choice. **The Dock lands on the wrong display after wake, unlock or reboot** in every tool. DockAnchor #5 was closed while users still reproduced it with "secondary display … below the primary", and #38 (an external above a MacBook) is still open ([DockAnchor #5](https://github.com/bwya77/DockAnchor/issues/5); [#38](https://github.com/bwya77/DockAnchor/issues/38)). Every tool's answer is reactive: re-anchor after a delay. DockAnchor waits 3 s after wake and 1 s after unlock, mac-dock-lock waits 3 s and also polls every 3 s, and DockLock checks after wake and moves only if the Dock is wrong ([DockAnchor L248–L324](https://github.com/bwya77/DockAnchor/blob/HEAD/DockAnchor/DockMonitor.swift#L248-L324); [mac-dock-lock L370–L419](https://github.com/darrenoakey/mac-dock-lock/blob/HEAD/Sources/main.swift#L370-L419)). DockAnchor waits 2 s after a display is enabled because firing immediately "can cause validateCurrentAnchorDisplay() to see a partial list" ([DockAnchor L1267–L1400](https://github.com/bwya77/DockAnchor/blob/HEAD/DockAnchor/DockMonitor.swift#L1267-L1400)).

**File drags get past a `mouseMoved`-only tap** (DockAnchor #30, confirmed by three users); DockPin also masks `*MouseDragged` ([DockAnchor #30](https://github.com/bwya77/DockAnchor/issues/30)). **Blocking the whole edge traps the pointer and breaks Universal Control.** DockAnchor #7: the pointer could not reach an iPad under a blocked monitor ([DockAnchor #7](https://github.com/bwya77/DockAnchor/issues/7)). **A bare-warp restore leaves Dock icons magnified**, because the Dock never sees the pointer leave. DockAnchor #35 hit this on every unlock on a three-display Mac ([DockAnchor #35](https://github.com/bwya77/DockAnchor/issues/35)). **Synthetic motion looks like user input to other apps.** Auto-relocating after every unlock made ChatGPT's "Locked use" relock, and the reporter asked for an option to disable auto-move ([DockAnchor #39](https://github.com/bwya77/DockAnchor/issues/39)). **Full-screen apps and screen sharing break through** ([DockLockPro #3](https://github.com/JulyIghor/DockLockPro/issues/3), [#6](https://github.com/JulyIghor/DockLockPro/issues/6)). **A move needs a still mouse and no open menus**: DockLock "can't relocate the Dock when you are constantly moving the mouse or the context menu or the control center is opened" ([DockLockPro #9](https://github.com/JulyIghor/DockLockPro/issues/9)).

## Scenario-by-scenario expectations

"Exposed" means the Dock-edge intervals that no other active display touches. Confidence: **H** = consistent reports plus a mechanism, **M** = several reports or strong inference, **L** = single, conflicting or no report.

| Scenario | What macOS does | What a clamp + warp-and-push tool should expect | Conf. |
|---|---|---|---|
| Side by side, bottom Dock (any heights) | Each display's bottom edge is exposed; Dock follows a push on any of them | Clamp the full bottom edge of non-anchors; push at mid-edge works | H |
| Side by side, left/right Dock | Only the outermost display on that side has an exposed edge; Dock lives there | An anchor that is not outermost has zero exposed stretch: show the covered-edge message. Never clamp the inner shared edge (it would wall off crossing) | M |
| Stacked, identical widths, bottom Dock | Upper display's bottom fully covered; Dock stays on the lower one even when the upper is main ([256192595](https://discussions.apple.com/thread/256192595)) | Upper anchor unreachable: message plus "offset a few points in Arrange". Lower anchor: clamp only the upper's exposed stretches (none) | H |
| Stacked, upper narrower and inside the lower's span | Upper fully covered | Same as identical stack | H |
| Stacked, upper wider (e.g. laptop centred under an ultrawide) | Free stretches either side of the laptop; mid-edge leads onto the laptop | Push in the widest free stretch, not mid-edge (Dock Tile's measured failure, `DockLockEdgePointTests`); try the other stretch if it fails | H |
| Offset stack (upper hangs past the lower's end) | The hanging part is exposed | Push in the hanging stretch; narrow overhangs have an unknown minimum width | M |
| Two monitors over a centred laptop | 15.0: Dock reached neither top monitor; offsetting fixed it ([255762225](https://discussions.apple.com/thread/255762225)). 15.1+: each top monitor's outer stretch should work | Per-anchor exposed stretches; on 15.0.x expect failure on every stretch that touches a seam | M |
| 2×2 grid / 3-wide plus 1 above | Top row fully covered; only bottom-row bottoms qualify ([DockPin #1](https://github.com/green2grey/DockPin/issues/1)) | Top-row anchors unreachable; clamp only exposed stretches so the pointer still crosses into the top row and to Universal Control devices | H |
| Corner-only (diagonal) touch | Unknown: the overlap interval has zero length | Treat the edge as fully exposed; measure | L |
| Vertical stack, left/right Dock | Both displays have an exposed side edge. Reports conflict: topmost (2016) vs bottom/main only (15.7.2) ([256184856](https://discussions.apple.com/thread/256184856)) | The push may simply be ignored; verify after each attempt and report failure honestly | L |
| Auto-hide on | Same placement rule; reveal needs the push | `visibleFrame` detection reads zero; fall back to the AX or CGWindow detector; without one, success can't be verified | M |
| "Displays have separate Spaces" off | Dock pinned to the main display; pointer pushes do nothing ([MacRumors](https://forums.macrumors.com/threads/hide-menubar-but-keep-window-snapping.2446351)) | Don't clamp or push. Tell the user the Dock follows the main display; changing the main display also moves the menu bar | H |
| Mirrored displays | No source; a hardware mirror set has one drawable surface in the active list | Use the active list, ignore mirror secondaries (as DockPin does); measure software mirroring | L |
| Sidecar (iPad) | Normal edge rules, except iPad *below* main: Dock could not return "offset or not" ([256165313](https://discussions.apple.com/thread/256165313)); reconnect pushes the Dock down ([DockLockPro #4](https://github.com/JulyIghor/DockLockPro/issues/4)) | Expect a jump on reconnect and re-anchor after it settles; an iPad-below layout may fail even with exposed stretches | L |
| AirPlay display | Normal edge rules ([256165313](https://discussions.apple.com/thread/256165313)) | Normal handling | M |
| DisplayLink (Tahoe 26.4) | Dock space can be reserved on two displays ([t-69877](https://www.displaylink.org/forum/archive/index.php/t-69877.html)) | `visibleFrame` detection can name the wrong display; prefer the window-based detector or require agreement | L |
| Display sleep / wake | OS resets the Dock to the primary display on wake ([DockAnchor](https://github.com/bwya77/DockAnchor/blob/HEAD/DockAnchor/DockMonitor.swift#L248-L324)) | Re-check 1–3 s after wake or unlock and move only if wrong; a sleeping display is not "active". Whether its edge still counts as a seam is unknown | M |
| Hot-plug a display below the anchor | Dock jumps to the new screen ([DockAnchor #16](https://github.com/bwya77/DockAnchor/issues/16)) | Debounce the reconfiguration burst; act only on completion callbacks, then recompute the stretches | M |
| Full-screen app / screen sharing | Can break locks ([DockLockPro #3](https://github.com/JulyIghor/DockLockPro/issues/3), [#6](https://github.com/JulyIghor/DockLockPro/issues/6)) | Accept; don't fight it with retries | M |
| macOS 15.0 | Partly covered seams fail too | Stretch-adjacent pushes may all fail; message should not blame the arrangement alone | H |
| macOS 15.1–15.7, 26.x | Exposed-stretch rule as above | Baseline | M |
| macOS 27 | No rule change found; ⌘Tab follows the active window, not the Dock ([DockLockPro #11](https://github.com/JulyIghor/DockLockPro/issues/11)) | Baseline; re-verify, since two tools needed 27 fixes | L |

## Design implications for Dock Tile's Dock Lock

### A plain message when the anchor's edge is fully covered

The uncommitted `dockEdgePoint` falls back to the middle of the edge when `exposedSegments` is empty, then spends its ~6 s push budget on a move that cannot succeed (local: `DockLockManager.swift`). That case should end before any warp. The seam already exists: an empty `exposedSegments(of:edge:others:)` is the signal. Make `dockEdgePoint` return `nil` there instead of falling back to the middle, and add a distinct move state, not `.failed`. The message has to give the cause and the fixes the evidence supports. For example: "macOS can't show the Dock on *Studio Display*: *MacBook Pro*'s screen sits along its whole bottom edge. In System Settings › Displays › Arrange, slide one display a little so part of the edge is free, put the Dock on the left or right, or choose another display." Offsetting by a few points is the remedy users confirmed ([DockPin #1](https://github.com/green2grey/DockPin/issues/1); [Apple Community 256165313](https://discussions.apple.com/thread/256165313)). Show the same state in the picker before the user selects such a display, and recompute it on every display change, because a setup key can now map to an anchor that has become unreachable.

For the clamp, follow DockPin: when the anchor is unreachable, install no zones. Clamping everywhere else would hold the Dock on a display the user never chose and trap the pointer at seams. The rule's side-Dock form needs its own wording ("only the leftmost display can hold a left Dock"), because there the cause is an outermost-display constraint, not overlap. Two more preconditions deserve the same treatment rather than a silent failure. The first is separate Spaces being off (the `com.apple.spaces` `spans-displays` key named in the brief, not independently sourced here). The second is a missing post-event grant: `CGPreflightPostEventAccess()` false while `AXIsProcessTrusted()` is true, a state seen on Sequoia ([Apple Forums 758554](https://developer.apple.com/forums/thread/758554)).

### Trying every free stretch, widest first, with a verified result per attempt

Pressing on the widest stretch fixes the owner's laptop-under-ultrawide layout. One stretch is still one guess, though: a stretch that measures as exposed can fail to take the Dock (the 15.0 seam behaviour, the iPad-below anomaly, and pushes landing near a neighbour), and users report the ends of a free stretch working more reliably than the middle ([OWC](https://eshop.macsales.com/blog/48027-how-to-move-the-dock-from-one-monitor-to-another-on-a-mac/)). Return all stretches from the seam, ordered widest first. For each one, pick a target at the midpoint, at least 8 pt from an outer display corner when the stretch allows, so hot corners stay quiet. The 8 pt figure comes from an unreadable pika-tools PR ([PR #48](https://github.com/dev-pikapik/pika-tools/pull/48)), so treat it as a starting value. Assert with `CGGetDisplaysWithPoint` that the point 1 pt past the edge lies on no display. Then glide in and push, check `currentDockDisplayID()`, and move to the next stretch if the Dock hasn't arrived. Split the existing 6 s budget across stretches, for example 2 s each with a total cap, rather than giving 6 s to each one. Order stretches below a minimum width (unknown; DockPin keeps anything over 0.5 pt) last, and name them in the failure message ("the free part of the edge is only 12 pt wide").

Three details matter for every attempt. **Restore with a warp plus one posted `mouseMoved` at the origin**, as DockPin does ([DockReanchorer.swift](https://github.com/green2grey/DockPin/blob/HEAD/Sources/DockReanchorer.swift#L13-L71)). The current bare `CGWarpMouseCursorPosition(origin)` is exactly the stuck-magnification bug in DockAnchor #35. **Post from a dedicated `CGEventSource`** rather than `nil`, so the code controls suppression explicitly: keep it during the push and set it to zero for the restore. **Move only when the Dock is wrong, and not while the user is moving the mouse.** The display-change path already checks first. Wake and unlock paths that move without checking are what produced DockAnchor #39. When detection returns `nil` (auto-hide plus no Dock window), make a single attempt on the widest stretch and report "can't confirm" rather than "failed".

## Conclusion

The question "which display shows the Dock" has a geometric answer, not a preference-based one, and that turns Dock Lock's hardest failures into predictable ones. A layout with no free edge on the anchor isn't a flaky move. The tool can tell before touching the cursor that the move is impossible, and it should say so in the user's terms. The remaining unpredictability is narrow and nameable: the minimum free width, how long the push must last, which stacked display a side Dock prefers, and post-wake resets. Each of these is a measurement to make once per macOS release, not a constant to keep retuning.

The prior art also points to a scope limit. DockPin, the tool with the best geometry, still never verifies that its move worked. DockAnchor, the most popular, verifies but restores the cursor badly and moves too eagerly. Dock Tile already verifies. Adding widest-first retries, a restore that posts an event, check-before-move on wake, and an honest "unreachable" state would make it the only tool in this set that is correct about geometry and also proves each move against the Dock's actual position.
